## 1. 背景与执行约束

### 1.1 已知现象与审查结论

用户反馈项目卡顿、不丝滑。只读审查发现的共同问题是：

> 小范围内容变化触发大范围重复工作；部分节流只合并发送，没有合并之前的计算、复制和读取。

审查覆盖 React Webview、Java 消息处理、Node Codex 桥接、历史分页及输入框。现有证据足以证明下述重复工作，但尚未完成真实 JetBrains/JCEF 性能录制，不能将每项问题直接等同于实际卡顿的唯一原因。

### 1.2 已完成的审查验证

- 8 个相关前端测试文件、126 项测试通过。
- 实际 Hook 验证：完成一次文件修改后，30 次纯文字更新触发 90 次存储读取、30 次存储写入。使用计数存储替身，证明的是调用次数，不是物理磁盘耗时。
- 实际 Hook 验证：纯文字更新会改变 `findToolResult` 引用。
- 实际 Hook 验证：消息清空后，工具结果缓存仍保留旧 raw 对象。
- 长代码高亮做过 Node 合成微基准，200 / 1,000 / 3,000 行重复 JavaScript 的单次高亮中位数约为 6.0 / 24.1 / 74.7ms。这不是 JCEF 端到端测量，也不包含 DOM 成本。

- Markdown 测试出现 KaTeX quirks-mode 警告，但测试通过。

这些结果只作为交接基线；执行时须确认当前分支没有改变相关实现。上述临时 Hook 验证未作为测试文件保存，T0 需要将其转换为可重复的正式回归测试。

- CI 优先断言执行次数、读取字节数、挂载数量、缓存生命周期，避免不稳定的毫秒阈值。

- 功能测试通过不等于性能达标；必须有对应的工作量下降证据。
- 优化后不得引入丢消息、乱序、过期结果、选择丢失或滚动跳动。

### T1：[P1] 让纯文字更新不再使历史消息失去渲染缓存

**入口与定位：**

- `webview/src/hooks/useChatComputations.ts:199` — `findToolResult` 依赖整个 `messages`。
- `webview/src/components/MessageList.tsx:350` — 查询函数传递给每个消息条目。

**问题：** 流式更新改变查询函数引用，使所有挂载的历史消息无法通过浅比较跳过渲染。已有消息折叠减少挂载数量，但不能消除此问题。

- [x] 建立会话内工具结果索引，以工具 ID 定位结果。
- [x] 区分文本变化与工具结果变化；工具结果集合不变时复用索引快照和查询函数。
- [x] 对未改变的历史消息保持对象引用及渲染属性稳定。
- [x] 工具结果实际更新时必须正常刷新对应卡片，不允许靠忽略属性变化掩盖问题。
- [x] 纯文字更新不重复查找全部未完成工具；新增结构性消息时再更新索引。
- [x] 检查消息列表自身为工具签名提取结果的工作，复用未变化消息的派生结果。

**回归测试：**

- 30 次尾部文字更新，旧消息的组件函数不因此重复执行。
- 工具由 pending 变为成功、失败或拒绝时及时更新。
- 同一工具结果被后续快照修订时，不能返回旧值。
- 消息合并、历史追加、相同内容不同消息不发生错误复用。
